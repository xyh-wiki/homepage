# JSON 文本清理与格式化：从报错定位到结果核对

JSON 报错通常不是工具本身的问题，而是输入文本在结构上不符合 JSON 语法。格式化工具可以帮助定位和阅读结构，但不会替你判断字段含义，也不会自动证明数据适合投入生产。

## 先区分 JSON 和“看起来像 JSON”的文本

标准 JSON 使用双引号表示对象键和值，布尔值只能是 `true` 或 `false`，空值写成 `null`，最后一个字段后不能留下多余逗号。JavaScript 对象字面量可以使用单引号、未加引号的键或注释，但那不一定是合法 JSON。

例如下面这段 JavaScript 写法不能直接当作标准 JSON：

- 使用单引号包裹字符串；
- 键名没有双引号；
- 数组或对象末尾存在多余逗号；
- 在内容中夹带注释。

## 按错误位置逐层缩小范围

面对“第 N 行第 M 列”这类错误，不要立刻重写整个文件。可以先从报错位置向前检查最近的逗号、引号和括号，再确认当前层级是对象还是数组。很多错误发生在前一行，解析器只是到下一行才发现结构无法继续。

建议依次核对：

- `{}` 和 `[]` 是否成对；
- 字符串内部的双引号是否已转义；
- 相邻字段之间是否只有一个逗号；
- 数字、布尔值和 `null` 是否没有被误写成字符串；
- 文件开头是否包含意外的说明文字或代码围栏。

## 格式化后仍要检查内容

格式化只改变缩进和换行，不会判断字段是否拼写正确。例如把 `userId` 写成 `userid`，语法仍然有效；把金额写成字符串，语法也可能有效，但下游程序未必接受。

格式化之后，至少检查顶层类型、必需字段、数组是否为空、日期和时区表示，以及敏感字段是否应该出现在共享文本中。对接口响应，还要结合接口文档核对字段类型和兼容性。

## 清理敏感信息

密码、访问令牌、Cookie、私钥和客户数据不应直接粘贴到不清楚处理方式的在线工具中。即使工具声称在浏览器本地运行，也应先确认页面没有上传请求，并避免把原始内容复制到日志、截图或工单中。

分享错误样本时，可以替换真实域名、账号、邮箱和标识符，同时保留导致错误的结构。不要为了“可复现”而公开真实凭证。

## 什么时候应该使用工具

短小、非敏感的 JSON 可以使用 [EditText Lab](/services/text-tools/) 做格式化和基础检查。涉及生产配置、个人资料或未脱敏接口响应时，优先在本地编辑器和项目已有校验命令中处理，并保留原始文件。

一个可靠的流程是：复制副本、定位语法错误、格式化、核对字段含义、运行项目测试，最后才把结果交给下游系统。工具负责减少机械操作，最终判断仍需要由维护者完成。
